# Admin app and moderation

Part of the decisions in `docs/DESIGN.md` section 7. Rules: Slice 7: admin app, roles, bans, strikes, removals, reports, audit, support.

- Role freshness (decided 2026-11-05, slice 7): the role is still copied into the session JWT at sign-in, but the API no longer trusts it. `JwtAuthGuard` looks the user up in the database on every authenticated request (the token only has to carry `sub`; its email and role claims are ignored) (one primary-key query) and uses the database's role and email; a missing user is 401, a banned user (`User.bannedAt` set) is 403 `BANNED`, and `OptionalJwtAuthGuard` treats a banned user as signed out. A demoted admin or banned user therefore loses access on their next request, and a promoted user gains it at once. `AdminGuard` (after `JwtAuthGuard`) allows only `role = ADMIN`. A banned user cannot start a sign-in (403 `BANNED` after the right password) or finish one, and a socket connecting with a banned user's token is refused (the account is checked in a Socket.IO middleware, so the private room is joined before the client hears `connect`). A socket the server refuses is told why just before it hangs up (`connect_error_auth` with a code: `BANNED`, `INVALID_TOKEN`, or `UNAVAILABLE` when the database could not be asked, which is not blamed on the visitor); the web client reconnects after 2 seconds, except for `BANNED`. A socket that is already connected when a ban lands is told `BANNED` and hung up by the ban action (see "Bans and strikes" below).
- Admin app shell and sign-in (built 2026-11-05, slice 7, step 2): `apps/admin` (port 3001) has its own Auth.js setup and the slate and indigo theme. Sign-in is the storefront's two steps (password, then the emailed 6-digit code) and only an account whose role is ADMIN gets a session; anyone else gets the same message as a wrong code. There is no sign-up: the first admin is made with `yarn workspace @auction/db make-admin <email>` (`--remove` demotes; it works on whatever `DATABASE_URL` points at). It uses its own cookie names (`admin.session-token`, `admin.csrf-token`, `admin.callback-url`) because on localhost the storefront and the admin app share cookies, and sets `AUTH_URL` to `ADMIN_URL` (default `http://localhost:3001`) so the storefront's value in the shared `.env` does not leak in. Every console page asks the API `GET /admin/me` on each request (`requireAdmin`): a demoted admin or banned account is sent to `/sign-out?denied=1`, which ends the session and shows "That account is not allowed to use the admin app"; the real lock is the API's `AdminGuard`, never this app. The console is a slate sidebar (Overview so far, signed-in email, Sign out) and a content area. Own Vercel project: set `AUTH_SECRET` (same as the API), `API_URL` and `ADMIN_URL` there.
- Reports queue and question log (built 2026-11-05, slice 7, step 3): three admin-only API routes behind `AdminGuard`. `GET /admin/reports?status=OPEN|HANDLED&limit=` lists reports (open ones oldest first, handled newest first) with the words as written, reason, whether it was a question or an answer, `postedAt`, the reporter (null for a report the site raised itself), the author of the reported post (the asker, or the listing's seller for an answer) and the listing, and carries `openCount`; people and listings are looked up by id and show as null or a deleted user when gone, since reports have no foreign keys. `POST /admin/reports/:id/handle` sets `HANDLED` and `handledAt` with a guarded update, so a second click keeps the first time (unknown id 404); the existing clean-up deletes handled reports 30 days after the auction ends. `GET /admin/question-log?questionId=&listingId=&actorId=&limit=` lists `QuestionLog` newest first with the text before an edit. The admin app has Reports (Open / Handled tabs, "Mark handled", a link to that question's log) and Question log pages in the sidebar. Report text is shown as plain text. Not decided yet: whether rating comments get a report button (see REMAINING-WORK); this step covers questions and answers only. 
- Admin listing removal (decided and built 2026-11-05, slice 7, step 4, first part): an admin takes a live or upcoming auction down with `POST /admin/listings/:id/remove` (`{ reason }`, 1 to 500 characters; `GET /admin/listings/:id` is the summary the admin page reads). **Decision (owner, 2026-11-05): end it early with no sale**, whatever the bids and the reserve, rather than refusing or cancelling and messaging the bidders by hand. It reuses the close path: `AuctionCloseService.closeRemoved` sets `endsAt` (and `startsAt` if still in the future) to now, `removedAt`, `removedById` and `removalReason`, then runs the normal close in the same transaction, which gives outcome `NO_SALE` (`NO_BIDS` when nobody bid), no winner, no order, and one "auction ended" email to every bidder, the high bidder included. The email says a moderator ended it and the bid does not need to be paid. The close statement accepts a row with `removedAt` set even if its end time rounds a fraction of a millisecond ahead of the database clock, and a removal that cannot close throws so the whole transaction rolls back (an early version could leave a listing half removed). The listing leaves the search index at once. Refusals: 404 unknown, 409 `NOT_PUBLISHED` for a draft, 409 `ALREADY_CLOSED` for an ended auction, sold ones included, and 409 `AUCTION_ENDED` when the end time has passed but the close has not run yet (a won auction is never turned into "no sale"; the normal close sells it). Afterwards bids get `NOT_LIVE`, the seller's relist answers 409, and the seller can neither delete the listing nor change its description or photos (409), so it stays as the record, and `GET /listings/:id` carries `removed` (everyone) and `removalReason` (seller only); the listing page shows a banner and hides "list it again". The admin app has a listing page (`/listings/<id>`, reached from a report's listing title) with the summary, a reason box and a confirm before it removes. Not built: removing a sold auction.
- Bans and strikes (decided and built 2026-11-05, slice 7, step 4, second part): the admin app has a Users page (search by username, email or id, a "banned only" filter) and a page per account with its details, its strikes and the ban controls. API, all behind `AdminGuard`: `GET /admin/users` and `GET /admin/users/:id`, `POST /admin/users/:id/ban` (`{ reason }`, 1 to 500 characters) and `/unban`, and `DELETE /admin/strikes/:id`. A ban is one guarded update, so two admins banning the same person at once ban once (the other gets 409 `ALREADY_BANNED`); an admin cannot be banned (409 `CANNOT_BAN_ADMIN`, demote them first), and unbanning someone who is not banned is 409 `NOT_BANNED`. It takes effect on the person's next request (the guard reads the database every time) and, at once for any page they have open: `RealtimeGateway.suspendUser` tells their sockets `connect_error_auth` `BANNED` and hangs them up, across machines through the Redis adapter, and the web client then sends the page to `/suspended` and does not reconnect. On the storefront, `authedApiFetch` sends any call that meets 403 `BANNED` to `/suspended`, which says the account is suspended and signs the browser out; signing in with a banned account says "This account has been suspended." (admin sign-in already did). A ban does not touch the person's listings, bids or orders and does not hold back a payout (decided earlier); an admin removes a listing separately. Clearing a strike deletes that one row, so a person at `MAX_STRIKES` can bid again once they are under it; strikes are listed with the listing they were for. Not built: banning an admin without demoting them, and clearing all strikes in one click.
- Admin audit trail (decided and built 2026-11-06, slice 7 follow-up, owner's choice): `AdminAction` rows (no foreign keys, like `QuestionLog`) record which admin did `BAN_USER`, `UNBAN_USER` (both with the reason typed for a ban), `CLEAR_STRIKE` (target is the user, reason holds the strike id), `REMOVE_LISTING` (with the reason) and `VIEW_ORDER` (each time an admin opens an order, since it shows both addresses). Bans, restores and strike clears are written in the same transaction as the change, and only when it really happened (a refused second ban or a 404 writes nothing); a removal and an order view are written just after, so a failure to write the row fails the request. **Kept for ever**, no clean-up. A repeat `VIEW_INVOICE` by the same admin for the same order and party within a minute is not written again (a double click or prefetch). `GET /admin/audit?adminId=&targetId=&limit=` lists newest first; the admin app has an Audit log page in the sidebar with links to the admin and the target. Not built: recording sign-ins, and who handled a report.
- Admin overview and listings page (built 2026-11-06, slice 7 follow-up): `GET /admin/overview` returns counts (open reports, live and upcoming auctions, orders awaiting payment, paid orders not yet shipped, banned accounts, accounts); the Overview page shows them as links to the matching filtered list, and the sidebar shows the open-report count next to Reports (the layout and page share one request). `GET /admin/listings?q=&phase=upcoming|live|ended|removed&limit=` lists published listings newest first (`q` matches id, title or seller username; drafts are not listed) and the admin app has a Listings page with search and a state filter, linking to the existing listing page.
- Removing a reported post (built 2026-11-06, slice 7 follow-up): `POST /admin/reports/:id/remove-post` takes the reported question or answer down and closes every open report about that same post, in one transaction. A question is deleted the way its asker deletes it (so its answer goes too); an answer is taken back, which leaves the question open again for a new answer (its votes are cleared). It works after the auction has ended. If the post is already gone, or the answer was replaced since the report, nothing is removed and the reports are just closed (`removed: false`), so a double click or stale page is harmless. It writes a `QuestionLog` `DELETED` entry with the admin as actor and an `AdminAction` `REMOVE_POST` (target: the question id). The reports page has a red "Remove question/answer" button with a confirm. Not built: telling the author, and banning from the same screen (the author's name links to their page).
- Removed by moderation shows in place (decided and built 2026-11-09, owner's request): a question or answer a moderator removes is no longer deleted. `Question.moderatedAt` / `answerModeratedAt` mark it; the words stay in the database and the admin log but are never sent to the public. On the listing page the asker is shown as usual and the words are replaced by "This question/answer was removed by moderation. See what you can and cannot post", linking to `POLICY_LINKS.comments` (`/policies/comments`; the policy pages themselves do not exist yet, the link is a placeholder). A removed question hides its answer and its votes; a removed answer is final (the seller cannot answer again, edit or delete it); nobody can edit, delete, vote on or report a removed post. Moderated rows are purged 30 days after the auction ends, like deleted ones. A listing a moderator removed shows the public its seller and the message "This listing was removed by moderation" with a link to `POLICY_LINKS.listings` (`/policies/listings`, also a placeholder) instead of its title ("Removed by moderation"), description and photos; the seller still sees their own content, and the admin app still sees everything.
- Removing from the question log (built 2026-11-09, owner's request: "i cant delete any questions as an admin, unless theyre reported"): each conversation in the Question log has red "Remove answer" and "Remove question" buttons (only where that post is still up; `GET /admin/question-log` carries `questions`, the live state of each). `POST /admin/questions/:id/remove` (`{ target: "QUESTION" | "ANSWER" }`) takes the post down the same way a report removal does (a question goes with its answer; an answer is taken back and its votes cleared), closes every open report about that kind of post on the question, writes a `QuestionLog` `DELETED` entry and an `AdminAction` `REMOVE_POST` ("from the question log"), and answers `removed: false` when it was already gone.
- Moderation notices (built 2026-11-06, slice 7 follow-up): **a ban emails the person** ("Your account has been suspended", with the reason the admin typed), sent straight away and best effort (a failed send is logged, the ban stands) and not awaited, so a slow mail provider cannot hold up the admin's request; an unban emails the person "Your account has been restored" (added 2026-11-09, owner's request; same best-effort, not-awaited send, for the Unban button on a user's page and for "Unban and close" on a ban appeal). **A listing removal tells the seller** with an email (`PendingEndEmail` kind `REMOVED`, written in the close transaction and sent by the existing leased sweep, with the moderator's reason) and a saved bell entry (`LISTING_REMOVED`, key `removed:<listingId>`, "Your listing was removed", no live toast, saved after the close so the close's notification expiry does not hide it). The bidders' "ended early by a moderator" email is unchanged, and **every bidder also gets a saved bell entry** (`LISTING_REMOVED`, key `removed:<listingId>`, `data.bidder` true, "An auction you bid on was ended", added 2026-11-09 at the owner's request; no live toast, the unread count updates live, best effort after the removal). Not built: a live toast for the seller.
- Admin roles from the admin app (built 2026-11-06, owner's note): `POST /admin/users/:id/role` (`{ role: "USER" | "ADMIN" }`) makes an account an admin or an ordinary user again, with a "Admin role" box on the user page (confirm first) so `make-admin` is only needed for the first admin. Refusals (409): `CANNOT_CHANGE_OWN_ROLE` (another admin has to do it), `SAME_ROLE`, `BANNED` (a banned account cannot be made an admin), `LAST_ADMIN` (the admin rows are locked with `FOR UPDATE` while they are counted, so two admins demoting each other at once cannot leave none). Writes an `AdminAction` `SET_ROLE` (reason `ADMIN` or `USER`) in the same transaction. A demoted admin loses access on their next request. The `LAST_ADMIN` rule has no automated test, because it counts every admin in the shared test database.
- Super admin (decided and built 2026-11-09, owner's request: "none should be able to, we should have a superadmin that can"): `User.isSuperAdmin` (a flag on an ADMIN account, so every ADMIN check still works). Only a super admin can promote or demote admins (`POST /admin/users/:id/role` answers 403 `SUPERADMIN_ONLY` to any other admin), and a super admin's own role cannot be changed from the app at all (409 `CANNOT_CHANGE_SUPERADMIN`); a super admin is made and unmade only from the command line, `yarn workspace @auction/db make-admin <email> --super` (plain `--remove` demotes and drops the flag). The existing rules stay (not your own role, not a banned account, never the last admin). `GET /admin/me` and the user summary carry `isSuperAdmin`; the admin app's user page shows "SUPER ADMIN" and the Admin role box says who may change what. Existing admins are not super admins until `--super` is run for them.
- Admin strikes (built 2026-11-06, owner's note: "admin can strike users based on reports"): an admin gives a strike with a reason from a user's page (`POST /admin/users/:id/strike`, `{ reason }`, 1 to 500 characters) or straight from a report (`POST /admin/reports/:id/strike-author`: the asker for a question, the listing's seller for an answer; the reason is built from the report's reason, the listing and the words, and the reports about that post are closed; the reports page offers "Remove question/answer", "Strike @user and remove question/answer" (one click; strike first, and the post is removed only if the strike was given) and "Mark handled"; a strike without removal is given from the user's page (decided 2026-11-09, owner's request)) (hardened 2026-11-06: if the reported question or answer was deleted, taken back or replaced since the report, the strike is refused with 409 `POST_CHANGED` instead of landing on whoever wrote the replacement; a strike and a promotion of the same account lock the user row, so they take turns). It counts like the strike for an unpaid order: `MAX_STRIKES` (2) blocks bidding, the admin can clear it, and the user page lists it as "given by an admin" with its reason. `Strike` gained nullable `reason` and `givenById` and an optional `listingId`; an admin strike has no order, so it takes `orderId` = `admin_<uuid>` to keep that column unique. An admin cannot be struck (409 `CANNOT_STRIKE_ADMIN`); 409 `NO_AUTHOR` when the report's author account is gone. Written with an `AdminAction` `STRIKE_USER` in the same transaction. **No new automatic strike triggers** (owner's decision): the system still strikes only for non-payment. The struck person is not emailed or notified (the listing page says their account has two strikes once they hit the limit); appeals are a later step.
- Question log as conversations (built 2026-11-06, owner's notes: search by username, email or listing; show which auction a question was said in; the "This question" link that went nowhere): `GET /admin/question-log` gained `q`, which matches a username, an email, an id or part of a listing title and returns a person's whole part in the conversations (what they wrote, the answers to their questions, and everything on the listings they sell) or all of a listing's; each entry carries its listing's id and title (null once the listing is gone). The page has a search box and, without a search or filter, shows only the 30 latest entries and a prompt. Results are grouped by listing, then by question, oldest first as a chat (answers indented, edits with the words before, deletions still readable). The old "This question" link, which pointed at the page it was already on, is gone; the Reports page's "Log" link still opens one question's conversation.
- Admin invoices (built 2026-11-06, owner's note: "admin should see the invoice for a paid order, as well as the seller's equivalent"): `GET /admin/orders/:id/invoice?party=buyer|seller` returns the same PDF the buyer's invoice or the seller's sale statement is (`invoiceDataOf` and `renderInvoice` from `apps/api/src/orders/invoice.ts`); 409 `NOT_PAID` when the order has no invoice yet, 404 unknown. The admin order page links both next to the invoice number, through a route handler in the admin app that adds the token. Each look writes an `AdminAction` `VIEW_INVOICE` (reason `buyer` or `seller`) like opening the order (owner's decision: keep order-view auditing and log invoice views too). Still read only: no refunds or corrections.
- Support and strike appeals (built 2026-11-06, owner's notes: "support button", "appeal to get strike cleared"; owner's decision: one form plus an admin queue): a signed-in person opens `/support` (menu item "Support"; the "you cannot bid, two strikes" note links to `/support?appeal`) and either asks a question or appeals one of their own strikes (picked from `GET /support/strikes`, which says which already have an appeal waiting). `POST /support` saves a `SupportRequest` (kind `GENERAL` or `STRIKE_APPEAL`, message up to 2,000 characters, status `OPEN` or `HANDLED`); an appeal for a strike that is not theirs or is already cleared is 404 `STRIKE_NOT_FOUND`, a second open appeal for the same strike 409 `ALREADY_APPEALED`, and a person is limited to 5 requests a day (429 `RATE_LIMITED`, `SUPPORT_RATE_LIMIT`); the duplicate check runs before the limiter so a double click spends no slot, and again with the insert under a per-person advisory lock so two simultaneous appeals save one. There are no replies in the app (private messages stay out of scope): the admin answers by email. The admin app has a Support page (Open and Handled tabs, a badge in the sidebar and a card on the Overview, each request with the person, their email, the strike with its reason, and the words); "Clear the strike and close" clears the strike (the existing `DELETE /admin/strikes/:id`) and closes the request (reworked 2026-11-06: one call, `POST /admin/support/:id/grant`, does both in one transaction with a guarded close first, so a failure cannot leave the strike gone and the appeal open, and an appeal another admin already closed clears nothing; the admin buttons now show the API's error instead of failing silently), "Refuse and close" / "Mark handled" only closes it (`POST /admin/support/:id/handle`, a guarded update so a double click keeps the first time, with an `AdminAction` `HANDLE_SUPPORT`). Clearing the strike emails the person "Your strike appeal was accepted" and refusing an appeal whose strike still stands emails "Your strike appeal was denied" (decided and built 2026-11-09, owner's request; best effort and not awaited, so the decision stands if the send fails); closing a general question or an appeal whose strike is already gone sends nothing. An appeal outlives its strike (`strikeId` is a plain id). **A suspended person writes from the suspended page instead** (decided and built 2026-11-09, owner's note "cant contact support when youre banned, wrong logic"): they cannot sign in, so `/suspended` has a form with the account's email and a message (also linked from the sign-in "suspended" message). `POST /support/suspended` needs no sign-in, saves a `SupportRequest` of kind `BAN_APPEAL` only when the email belongs to a suspended account with no appeal waiting, and answers 204 either way, so it reveals nothing about accounts; it is limited to 3 a day per email (429), whatever the email. The admin Support page shows it as a "Ban appeal" with the ban reason, and an "Unban and close" button (`POST /admin/support/:id/lift-ban`: one transaction with a guarded close first, so a request another admin already closed lifts nothing; writes `HANDLE_SUPPORT` and `UNBAN_USER` audit rows); "Refuse and close" only closes it. The person is emailed that their account was restored; a refusal sends nothing, so the admin answers by email. The signed-in form still refuses a suspended account. A "Support" link is also in the footer of every storefront page. Not built: a status page for the person's own requests, and emailing the person when a general question is closed.
- Admin order view (built 2026-11-05, slice 7, step 5): read only, behind `AdminGuard`. `GET /admin/orders?q=&status=&limit=` lists orders newest first; `q` matches the order id, the listing id or title, the invoice number, and the buyer's or seller's username or email. `GET /admin/orders/:id` is the whole order: the listing, the buyer and seller (username, email, real name, and whether the seller has a payout account), every amount (item price, platform fee, seller's share, delivery, what the buyer paid in all), the invoice number, the payment provider's reference and how many checkout attempts there were, the timeline (created, pay by, reminder sent, paid), the buyer's full delivery address and phone with the chosen option, the seller's pickup address and phone, the parcel (status, tracking code, label, in transit, delivered), the payout (status, due date, paid date, transfer reference; only for a paid order, worded by the same `payoutViewOf` the seller's own page uses) and the buyer's rating. This is the one place both addresses meet: the seller's order page still shows the buyer only a city and country, and the buyer's page never shows the pickup address (both are tested next to the admin view). The admin app has an Orders page (search, status filter) and an order page, linked from a user's page and a listing's page. Not built: any change to an order from the admin app (refund, cancel, correct an address).
- Orders needing attention (built 2026-11-11, owner asked for the most useful admin order tools; first of three, then internal notes and resending an email): `GET /admin/orders` takes `attention=expiring|overdue|not-shipped|not-delivered|payout-late|any`, and each row carries `attention` (the first kind it matches, or null). The kinds are states that clear by themselves, so one that lasts means something is stuck: payment due within 24 hours (a buyer about to be struck), past its payment deadline (the expiry sweep should have run), paid and not shipped for 3 days, shipped and not delivered for 7 days, delivered and the payout not sent 1 day after it was due. The thresholds are `ORDER_ATTENTION` in `packages/shared/src/orders.ts`; `admin-order-attention.ts` holds the database condition and the per-order check side by side, and a test checks they agree. The Orders page has a "Needs attention" filter and a tag per row; the Overview has an "Orders needing attention" tile that links to `attention=any`. Read only: no order changes.
- Admin order notes (built 2026-11-11, owner's choice of defaults; second of three order tools): an admin leaves a private note on an order with `POST /admin/orders/:id/notes` (`{ body }`, trimmed, 1 to 1,000 characters; 404 for an unknown order). Notes are shown oldest first, with the writer and the time, in a Notes section on the admin order page (`notes` in `GET /admin/orders/:id`), and the Orders list shows "N notes" next to an order that has any (`noteCount`). **Decision (owner): notes cannot be edited or deleted**, so the history stays as it was; they are for orders only. Never sent to the buyer or the seller. The `OrderNote` table has no foreign keys (like `AdminAction`), and each note is saved in one transaction with an `ADD_ORDER_NOTE` audit row whose reason is the note id (the note's words stay in `OrderNote` only).
