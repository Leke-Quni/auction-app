# Accounts, sign-in and sessions

Part of the decisions in `docs/DESIGN.md` section 7. Rules: Sign-in codes, session length, open account questions.

- Session length (decided and built 2026-11-09, owner's request, for security: someone who gets hold of a person's computer must not be able to bid): a signed-in browser is signed out after **2 hours without being used** on the storefront and **1 day** in the admin app, instead of 30 days. It is an idle timeout, not a time since sign-in: `proxy.ts` in each app runs Auth.js on every page request, which re-signs the session JWT and pushes its expiry (and the cookie's) forward, so a browser in use stays signed in. The lengths are `SESSION_MAX_AGE_SECONDS` in each app's `lib/session-lifetime.ts`. An older 30-day cookie is replaced by a 2-hour or 1-day one on its next request.
- An emailed 6-digit code on every sign-in (2026-10-30). Sign-up sends a code and goes to the code page. Later sign-ins: password, then code. A correct code verifies the email. Codes last 10 minutes, are single-use, lock after 5 wrong tries, and a new code voids the old. Signing up again with an unverified email replaces that account's name and password, so nobody can block an address they don't own; a verified email gives 409. After a code is sent, another for the same account answers 429 `CODE_COOLDOWN` for 30 seconds, checked only after the password is right so it reveals nothing. **Send a new code** (2026-11-06): the code page of the storefront and the admin app has a button, disabled for 30 seconds like the server's cooldown. `POST /auth/login/resend` takes only the email and always answers 204, whether or not it sent anything, so it reveals nothing about accounts. It sends only if the account's password step passed in the last 30 minutes (`LoginCode` still exists, even expired), the cooldown has passed, and fewer than 5 new codes were sent in this sign-in (`LoginCode.resends`, reset by the next password step); it never sends to a banned account. The new code replaces the old.
- Username squatting: an unverified sign-up holds its username. Decide a cleanup rule for stale unverified accounts before launch.
- Account deletion (decided and built 2026-11-12, owner's picks): **closing, not erasing.** Settings has a "Delete account" row. While something still stops it the row lists what, with links, and offers no form (`GET /me/deletion` returns the `blockers`): an auction of theirs that has bids (`LIVE_AUCTION_WITH_BIDS`), an auction they are the highest bidder in (`HIGH_BIDDER`), a purchase that is unpaid or paid but not delivered (`PURCHASE_IN_PROGRESS`), a sale that is unpaid, undelivered or not paid out yet (`SALE_IN_PROGRESS`). Unbid live or upcoming auctions do not stop it (they are ended with no sale, `removedById` = the seller, reason "The seller closed their account.") and neither do drafts (**deleted at once when the account is closed**, 2026-11-12, not kept for the 30 days: `POST /me/deletion` answers with `removedImageUrls`, the photo addresses no other listing uses, and the storefront's action deletes them from Blob with `deleteOwnBlobs`, the same way a hand-deleted draft's photos go). Confirming takes the password and a 6-digit code emailed to the account (`POST /me/deletion/code`, then `POST /me/deletion`; the code is a new `AccountDeletionCode` row, hashed, 10 minutes, 5 tries, 30-second wait and 5 an hour like the email-change code; no code is sent while something stops it). Confirming sets `User.deletionRequestedAt`: the account is **closed** at once, and `JwtAuthGuard` answers 403 `ACCOUNT_CLOSING` to everything except `GET /me/deletion` and `POST /me/deletion/restore` (`@AllowClosing()`); the storefront sends every such call to `/account/closing`, which shows the date it will be gone and a Restore button and a Sign out button. A closed account's public profile is 404, it gets no email (the outbox drops it), it is skipped for runner-up offers, and its email stays reserved. **Restoring** (sign in, press Restore) clears the flag and brings everything back except the auctions that were ended and the 30-day clock. After `ACCOUNT_DELETION_GRACE_DAYS` (30) an hourly sweep **anonymises** it (`AccountDeletionService.finalize`): email becomes `deleted-<id>@deleted.invalid` (so the real one is free for a new sign-up), username `deleted_<last 8 of the id>`, name "Deleted user", password and verification cleared, pickup address and payout account removed, sessions ended; its watchlist, notifications, codes, votes and queued emails are deleted, and `User.emailFingerprint` keeps a one-way HMAC of the old email (never the address). **Strikes carry over** (2026-11-12): when an account first verifies an email (the first sign-in code, or a password reset) whose fingerprint belongs to an anonymised account, that account's strikes move to the new one (`inheritStrikes`, `apps/api/src/users/email-fingerprint.ts`), so deleting and signing up again does not clear them; nothing moves before the address is verified, so someone who only types another person's address inherits nothing. Bids, orders (with their address snapshots, for invoices), ratings, questions and answers and ended listings are kept, shown with the placeholder name. After that it cannot be restored; the person can sign up again as a new account. A **banned** account cannot delete itself (every call is 403 `BANNED`, so an admin decides); a **struck** one can. **Display** (2026-11-12): a deleted account's username starts with `deleted_` (nobody can choose such a name, `DELETED_USERNAME_PREFIX`), and every storefront page shows it as "Deleted user" with no link to a profile (`displayUsername`, `isDeletedUsername` in `packages/shared`). Known gaps: a paid order whose seller was banned and cannot ship holds the buyer's deletion until it is sorted out; a Stripe connected account is not closed at the provider (nothing is owed by then, because a sale must be paid out before its seller can delete; it only matters before this goes live); the admin app still shows the placeholder name.
- Limits on the public auth endpoints (2026-11-11, from the audit): `login/start` allows 10 tries per email and 30 per address in 15 minutes, `signup` 5 per email and 10 per address an hour, `forgot-password` 3 per email and 10 per address an hour (constants in `packages/shared/src/auth.ts`). They are counted before any password hashing or lookup. Over the limit answers 429 `RATE_LIMITED`, except a forgot-password email over its own limit, which answers 204 and sends nothing, so it does not show the email has an account. The per-address limits use only the signed address the web server passes on (`signedClientIp`), never the connection's own, which is the web server's and shared by everyone; the admin app does not pass one yet, so it has the per-email limit only. Why: sign-in was open to unlimited password guessing, and forgot-password and sign-up could mail-bomb an inbox. A side effect: someone can lock out an email for 15 minutes by failing 10 times on it.
- Code tries are counted before the code is checked (2026-11-11, from the audit): sign-in and email-change codes claim a try with one guarded update (`attempts < 5`) and only then compare, so simultaneous guesses cannot exceed 5 whatever the concurrency. A correct guess also uses one try, which does not matter because the code is deleted once used. Why: counting after a wrong guess let parallel requests all see fewer than 5 tries (20 parallel guesses were counted as 15).
- Sessions end when the password changes or is reset (2026-11-11, from the audit): `User.sessionVersion` is raised by a password change or reset. Sign-in returns it, the storefront and admin cookies keep it (`sv`), and every API token and realtime token carries it. The API refuses a token whose `sv` differs from the account's (a token without `sv` counts as 0, so sessions from before this change last until the first password change). Changing the password from settings returns the new number and the browser doing it keeps its own session; every other browser is signed out on its next request. An open WebSocket is only checked when it connects, so it lasts until it reconnects (see the realtime token note in the audit). Why: a stolen session used to stay valid for its whole life after the owner reset the password.
- Email-change codes (2026-11-11, from the audit): asking for a code for a new address now waits like a sign-in code (`LOGIN_CODE_COOLDOWN_SECONDS`, 429 `CODE_COOLDOWN` with `retryAfterSeconds`, measured from the pending change's `createdAt`) and is capped at 5 an hour per account (`EMAIL_CHANGE_RATE_LIMIT`, 429 `RATE_LIMITED`). A wrong password or an address already taken answers first and uses none of the cap. Why: the form let a signed-in person send unlimited codes to any address.
- Save is locked until something changed (2026-11-12, owner's request): every form that edits something already stored (account settings rows, the default pickup address, a listing's pickup address, the listing form) keeps its Save button off while the form matches what is stored, and on again when it differs. A first-time save (no pickup address yet) is never locked. Why: pressing Save with no change only sends the same data again. Not covered: forms that do an action and store nothing to edit (sign-in, bids, questions, support, ratings, shipping at checkout, admin moderation and notes).
- **Accounts:** first name, last name, and a unique public username (3-20 chars of lowercase letters, numbers, underscores; some reserved; changeable). Real names stay private. Sign-in is by email. Settings (`/account/settings`): names, username, email, password, pickup address. Changing email or password needs the current password; an email change is confirmed by a 6-digit code to the new address. Every new-password field is entered twice. Forgot-password emails a one-hour, single-use link that also verifies the email and does not sign in.
