# Tooling and hosting

Part of the decisions in `docs/DESIGN.md` section 7. Rules: Test runner, Fly, speed, DB pool, email, images, search host and sync.

- Query library for server data: React Query or SWR.
- Test runner Vitest; package manager Yarn 4 with the `node-modules` linker; Docker Desktop for local Postgres and Redis (2026-10-30).
- API host: Fly.io free trial, no card (owner won't add one). App `auction-api-leke`, region `fra`, `fly deploy -c apps/api/fly.toml --ha=false`. The trial stops the machine 5 minutes after each start and restarts it on the next request (+3-4 s). Consequence: the API can vanish mid-request, so bids use idempotency keys, state is re-checked after failures, the live feed reconnects and resyncs, and nothing lives only in API memory. Web on Vercel, database on Neon (Frankfurt), email on Resend.
- Speed (measured 2026-11-05): the app felt slow for three reasons. (1) The Vercel apps ran in Washington D.C. (the default, `iad1`) while the API and database are in Frankfurt, so every API call from a page crossed the Atlantic; `apps/web/vercel.json` and `apps/admin/vercel.json` now set `"regions": ["fra1"]` (the Vercel project's Function Region setting must agree). (2) Pages asked for their data one request after another: the listing page made 4 in sequence and the home page 2 waves; they now ask for everything at once (the listing page makes its order request second, only for an ended sale), with 100 ms added to every API call a load went from 236 to 121 ms (home) and from about 340 to 118 ms (listing), and `/categories` (an hour) and the top price (a minute) are kept by Next instead of being asked for on every view (`rarelyChanging`); the admin check `/admin/me` is shared by the layout and the page of a request. (3) The Fly trial stops the machine 5 minutes after each start, whatever `fly.toml` says (confirmed from Fly's own event log: started 15:18:15, stopped by Fly at 15:23:15), and the next request pays a boot of about 5 seconds; sockets drop and the background sweeps pause in between. It cannot be configured away without a card. To shrink the stopped time, ping `https://auction-api-leke.fly.dev/health` every minute from a free external scheduler (for example cron-job.org); with pings, the API is stopped for at most about a minute of each cycle instead of until the next visitor. Not done: moving the API somewhere that does not stop (the owner won't add a card), and a "waking up" message in the web app.
- Database pool (2026-11-06): `packages/db` sets the pool explicitly: `DB_POOL_MAX` (default 10) connections per process and `DB_CONNECT_TIMEOUT_MS` (default 10,000) to get one, after which the request fails rather than hanging (a bid answers 503 `BUSY`; the pg pool's timeout is a plain error with no Prisma code, so `bidFailure` matches its message; other routes would answer 500) behind bids queued on a hot auction's row lock.
- Email: the API sends through Resend directly (`RESEND_API_KEY`, `MAIL_FROM`); production refuses to start without a key; a failed send is 503. Without a verified domain, Resend's sandbox delivers only to the account owner's address. Gmail SMTP sender (2026-11-12, owner's request, so demo visitors can sign up without a paid domain): with `SMTP_USER` and `SMTP_PASS` (a Google app password) set, the API sends through Gmail (`smtp.gmail.com:465`, `SMTP_HOST`/`SMTP_PORT` override) and ignores Resend; `MAIL_FROM` defaults to the Gmail address. Why: Resend needs a verified domain to mail anyone but its owner, and the owner has no domain and pays for nothing. Limits: about 500 mails a day, and mail comes from a Gmail address, so it is for the demo, not production.
- Images: a public Vercel Blob store with OIDC and presigned uploads (no long-lived token). The browser uploads via a short-lived URL from `apps/web/app/api/uploads` (own folder, JPG/PNG/WebP, 5 MB). The API accepts only Blob URLs in the seller's own folder and reports removed photos; the web app deletes them, because OIDC works only on Vercel.
- Search host: self-hosted Typesense in Docker Compose, not Cloud (2026-11-02). Cloud's free allowance is one-time and may need a card; the Fly trial machine cannot host it. The code uses a `SearchIndex` interface, so Cloud can be swapped in. Without `TYPESENSE_URL`/`TYPESENSE_API_KEY` the API falls back to `PostgresSearchIndex`, built to match Typesense (whole words plus prefix on the last word, typo tolerance via `fuzzystrmatch`, synonyms, repeated letters cut to two, most-words fallback). `apps/api/test/search-parity.e2e.test.ts` requires equal results from both. Known difference: a swapped letter pair is two typos in Postgres, one in Typesense.
- Search sync is direct from the API, not through an outbox (2026-11-02): listing saves update Typesense; a sweep (start-up and every 5 minutes) and `reindex` repair gaps; searches also filter ended auctions by end time. `BidPlaced` partially updates price, bid count, final-chance and end time, throttled to once per auction per 5 seconds, but extensions go at once.
- Limits on search and photo uploads (2026-11-11, from the audit):
  - Search: `GET /search` allows 300 requests a minute per visitor address and `GET /search/suggest` 120 (`SEARCH_RATE_LIMIT`, `SUGGEST_RATE_LIMIT`), counted before any search runs; over the limit answers 429 `RATE_LIMITED`. The address is the signed one the web server passes on (the search page and the suggestions route do), or the caller's own when someone calls the API directly; an unsigned header is ignored. Like the other limits it lets requests through when Redis is down.
  - Results: a search shows at most the first 2,000 results (`MAX_SEARCH_RESULTS`: page times page size). A deeper page is refused with 400. The search page clamps its page links to the cap, and says so when there are more results.
  - Uploads: before the web app issues an upload token for a photo it asks `POST /uploads/authorize`, which allows 30 a person an hour and 100 a day (`UPLOAD_HOURLY_RATE_LIMIT`, `UPLOAD_DAILY_RATE_LIMIT`). The counters live in the API because the web app has no Redis. Over the limit answers 429; if the API cannot be asked, no token is issued. A request body that is not JSON now answers 400, not 500. Worst case a person can still add 100 photos of 5 MB (500 MB) a day, which is the cost of not having a way to count the Blob store; deleting unsaved photos still depends on the browser's discard call.
- Condition filter takes several values (2026-11-11, owner's request): the sidebar shows the five conditions as checkboxes instead of a drop-down, and a listing matches when it has any of the ticked ones. `GET /search?condition=NEW,GOOD` (a comma list; a repeated `condition=` parameter works too, and a single value as before; duplicates count once; an unknown value or an empty one is 400). Typesense filters `condition:=[NEW,GOOD]` and the Postgres search `condition::text = ANY(...)`, and `search-parity.e2e.test.ts` still requires the same results. On the storefront the URL keeps the list in one parameter (`condition=NEW%2CGOOD`; the form itself sends repeated parameters, which the page and the header search read with every value, in the order of the form), the header search carries the list along, and the active-filter chips show one chip per ticked condition, each removing only itself.
- **Search:** Typesense with typo tolerance, filters (category, one or more conditions, price range, ending within 24 hours) and sorts (best match, ending soonest, ending latest, newest, most bids, fewest bids, price; "ending latest" and "fewest bids" added 2026-11-05). Only live and upcoming auctions appear, except that "ending latest" (like the "ending within 24 hours" filter) lists only live ones: an upcoming auction has not started (decided 2026-11-05). Synonyms are in `apps/api/src/search/synonyms.ts` (one-way general words such as "shoes" finding sneakers; spelling variants). Search is 503 when Typesense is down. Best match is the default sort with or without search words (decided 2026-11-12, owner's request; before, no words meant newest): without words there is nothing to match, so it lists the most active auctions first (most bids, then soonest end), which is also how the home page lists auctions, and clicking the logo goes to `/`, which has no filters and Best match. "Newest" orders by when the seller pressed Publish. The search page and home page share a sidebar of filters; ticking a box or changing the price waits for Apply, but choosing a sort applies the whole form (conditions, price, ending soon), so the results never contradict what the sidebar shows (2026-11-12, owner's request; an earlier version also applied on every price change, which reloaded the page while the owner was still adjusting it). The header search keeps filters as removable chips, is hidden on auth pages, and does nothing when empty. Recent searches (last 8) are kept in the browser's `localStorage` only. Suggestions as you type (2+ letters, 5 titles, debounced) use the same `SearchIndex.search`; any failure shows nothing. Arrow keys and Enter work on both lists. Search is limited per visitor address (300 searches and 120 suggestions a minute) and shows at most the first 2,000 results (see `docs/decisions/tooling-hosting.md`).
- Seed script `yarn workspace @auction/db seed [count] [--users N] [--owner <email>] [--allow-remote --confirm-host <host>]` (count default 1000, 0 removes; users default 40, 30 to 2,000): sample accounts (`@seed.local`, cannot sign in) and listings in every state, with bids following the real rules (2026-11-12, proxy bidding: every bulk bid is a maximum equal to its own amount, so only the named scenario `proxy-defended` has a hidden maximum, built through `resolveProxyBid`; each bidder's maximum is written to `AutoBid`). Ended auctions are closed the way the app closes them, and a sale has an order at some stage (awaiting payment inside its 48 hours, paid, shipped, delivered, rated, paid out, or not paid: a strike, and the item offered to the next bidder or no sale), with the app's own fee, delivery price and carrier timings. On top of the bulk it makes named scenarios (`packages/db/src/seed-scenarios.ts`): an auction extended twice, one at its final chance, three that close within minutes (sold, no sale, no bids), a 60-bid war with 25 watchers, questions and answers in every state with reports of every reason (open, handled, site-flagged) and their question log, a banned account, accounts with one and two strikes, moderator-removed listings, drafts, and a very expensive, a one-euro and an eight-photo listing. With `--owner` (a real account that already exists) that account is also given purchases at every stage (including one that gets its "24 hours left" reminder, an offer after a non-payer, a parcel that the fake carrier delivers while the API runs, a rated order and a strike), bids that lead, are outbid and are at their final chance, an auction that closes in four minutes with the owner winning, a watchlist with a queued "ending soon" email, notifications, questions, and their own listings from draft to delivered. Everything has an id starting `seed_` or belongs to a sample account, so running it again replaces its own data and nothing else, and `seed 0` removes all of it. The scenario times are relative to the moment it runs, so run it again to refresh them. It refuses to run unless the database is local; a remote one needs `--allow-remote` and the exact host typed after `--confirm-host` (it never runs when `NODE_ENV` is production, and never prints the connection string). Run `yarn workspace @auction/api reindex` afterwards when Typesense is used (a deployment that searches Postgres needs nothing). The Resend sender skips any address ending `@seed.local`, so the live API never tries to email sample accounts when it closes their auctions. Bot bidder: `yarn workspace @auction/api bot <listingId> [--every <s>] [--max <n>] [--proxy]` bids through the HTTP API so realtime can be watched solo; local API only. With `--proxy` each bid is a hidden maximum between the minimum and five times it, so defended bids and takeovers show up (2026-11-13; the bot's user names were also fixed to the seed's four-digit ones).
- Deploying proxy bidding (2026-11-13): the migration `20261112140000_proxy_bidding` is additive (the `AutoBid` table and the `Bid` columns `kind`, `maxCents`, `outcome` and `seq`) and backfills every existing bid as a maximum equal to its own amount, so auctions that are live at deploy time carry on as if every bid had been a maximum. Order: (1) apply it to Neon (`DATABASE_URL=<Neon url> yarn workspace @auction/db migrate:deploy`) and check that `prisma migrate status` against Neon says the database is up to date; the new API fails every bid without it. (2) Deploy the API: `fly deploy -c apps/api/fly.toml --ha=false`. (3) Deploy the storefront on Vercel. The API goes first because its bid answer only adds fields and the wire field stays `amountCents`: until the storefront is deployed, the old pages keep working (a bidder in front sees no raise box and an older bid box wording). A new storefront on an old API also degrades safely (no outcome is read as leading, no known maximum shows no raise box). The admin app has no change to deploy. Rolling back the code is possible, but an auction that already has proxy bids loses its hidden maximums (the old code ignores `AutoBid`), and its automatic and hidden-raise rows then look like ordinary bids, so roll back only between auctions or accept that. Seed data: run `yarn workspace @auction/db seed` again locally to get the `proxy-defended` scenario.
